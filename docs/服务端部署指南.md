# QuickShare 服务端部署指南

本文针对本项目当前代码，提供单台 Linux 服务器的完整部署流程。公网长期使用选择**域名 + HTTPS**；没有域名时，可选择**IP 直连**用于内网或短期测试。服务器已有 Nginx 时，使用 [已有 Nginx 部署指南](已有Nginx部署指南.md) 和 `docker-compose.nginx.yml`，无需启动 Caddy。部署方案只选一种，不要同时在同一台服务器启动。

示例使用 Ubuntu 24.04 LTS、Docker Engine 和独立的 `docker-compose` 命令。命令中的 `203.0.113.10` 是文档示例 IP，`share.example.com` 是示例域名，必须换成真实值。服务器命令使用 Bash；上传示例在 Windows PowerShell 执行。

## 1. 服务组成和部署约束

### 1.1 哪些组件运行在服务器上

| 组件 | 功能 | 当前部署方式 |
| --- | --- | --- |
| LiveKit | 房间、WebRTC 信令、媒体转发、TURN/UDP | Docker，Linux host 网络 |
| Token 服务 | API 鉴权、建房、进房 Token、房主管理校验、异常房间清理 | 从 `server/token-service` 构建 Node.js 容器 |
| Caddy | HTTPS 证书、API 与 WebSocket 反向代理 | 只在域名方案使用 |
| Electron 客户端 | 采集 Windows 屏幕、发布和观看画面 | 安装在用户电脑，不装到 VPS |

HTTPS 方案的数据路径如下：

```text
Windows 客户端
  ├─ HTTPS /api/* ──> Caddy :443 ──> Token 容器 :8080
  ├─ WSS 信令 ──────> Caddy :443 ──> LiveKit :7880
  └─ WebRTC 媒体 ─────────────────> LiveKit UDP / TCP / TURN

Token 容器 ── host.docker.internal:7880 ──> LiveKit RoomService
```

HTTPS 仅代理 API 和信令。媒体直接连接 LiveKit，**只开放 443 不能保证共享画面正常**；媒体端口也要放行。端口依据见 [LiveKit 官方端口说明](https://docs.livekit.io/transport/self-hosting/ports-firewall/)。

### 1.2 当前规模与恢复能力

- 当前部署为一个 LiveKit 实例和一个 Token 服务实例。Token 服务的房间锁在进程内，不能直接增加副本数量；扩容前需要共享的原子房间占用机制。
- 房间口令摘要、管理凭证摘要保存在 LiveKit 房间元数据里。仅重启 Token 服务且 LiveKit 仍运行、API 密钥不变时，现有房间的权限校验仍然有效。
- 当前模板未配置 Redis。重启 LiveKit 或整台服务器会中断共享；备份配置不能恢复正在进行的媒体会话，需要共享者重新开始。
- 无发布者的房间不显示在列表中；持续无发布者达到配置的宽限期后，后台会删除房间，包括仍有观众的空画面房间。
- 当前没有录制、系统声音共享、用户账号或按用户分配访问权限的功能。访问令牌是团队共享令牌。

### 1.3 服务器和带宽如何选

建议先用 2～4 核、4 GB 内存的云主机做小规模验证，再根据实际并发和码率压测调整。这是起始规格估算，不是并发承诺；转发压力还受网络、编码层和订阅数量影响。

SFU 的主要压力之一是服务器出站带宽。粗略按单路 8 Mbps 计算，10 个观众合计约 80 Mbps 出站，连续观看一小时约 36 GB 流量，实际还应留出协议开销和带宽余量。多个房间需要累计计算。公网 IP 应稳定，并能接收入站 UDP；HTTP 隧道或只支持网站的托管空间不适合作为此模板的媒体服务器。

## 2. 准备服务器和安装工具

### 2.1 基本准备

准备以下信息：

| 项目 | 示例 | 用途 |
| --- | --- | --- |
| 公网 IPv4 | `203.0.113.10` | 客户端连接、DNS 和媒体候选地址 |
| SSH 账号 | `deployuser` | 上传代码和执行部署命令 |
| 域名 | `share.example.com` | HTTPS 方案必需 |
| 部署目录 | `/opt/quickshare` | 保存源码和配置 |
| 云安全组权限 | 管理控制台中可修改 | 放行指定入站端口 |

确认服务器时间同步正常，时间偏差会影响 JWT 和证书校验：

```bash
timedatectl status
sudo timedatectl set-ntp true
```

检查端口是否已被其他服务占用：

```bash
sudo ss -lntup
```

HTTPS 方案需要本机 80/443 可用。已有 Nginx、Caddy 或网站服务的机器不能直接让两个程序绑定相同端口；应先规划统一反向代理，或为 QuickShare 使用独立服务器。

### 2.2 安装 Docker Engine 和 Compose

**如果服务器已经有可用的 `docker` 和 `docker-compose`，先运行下面的版本检查，无需重新安装，也不需要 Docker 的 Compose 子命令：**

```bash
sudo docker version
docker-compose version
sudo docker-compose version
```

最后一条用于确认通过 sudo 也能找到该命令。若普通用户能运行、sudo 提示找不到，执行 `command -v docker-compose` 获取路径，后文使用 `sudo /实际路径/docker-compose ...`。

HTTPS 方案使用 `host-gateway`，Docker Engine 需支持这一功能（20.10 或更新版本），参见 [Docker 20.10 发布说明](https://docs.docker.com/engine/release-notes/20.10/)。当前配置使用 Compose Specification，Compose 至少需要 1.27.0；较新的独立命令也支持该格式，参见 [Compose 配置格式说明](https://docs.docker.com/reference/compose-file/)。若版本检查显示更旧的 Python 版 Compose，并出现配置格式或环境变量解析错误，需要升级独立命令并核对它与 Docker Engine 的兼容性，命令写法仍保持不变。

下面的安装步骤只面向一台干净的 Ubuntu 24.04 服务器。已有 Docker/Podman/containerd 的机器应先核对兼容性，避免直接替换正在使用的容器运行时。Docker 安装参考 [官方 Ubuntu 安装文档](https://docs.docker.com/engine/install/ubuntu/)。

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl openssl python3 nano ufw
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin
sudo systemctl enable --now docker
sudo docker version
sudo docker run --rm hello-world
```

新服务器若没有 `docker-compose`，可按 [Docker 官方独立版安装说明](https://docs.docker.com/compose/install/standalone/) 安装。以下示例适用于 Linux x86_64；ARM64 机器需将下载文件名改为 `docker-compose-linux-aarch64`。已有可用命令时跳过，不覆盖原有安装。

```bash
uname -m
COMPOSE_VERSION=v5.5.0
curl -fL "https://github.com/docker/compose/releases/download/${COMPOSE_VERSION}/docker-compose-linux-x86_64" \
  -o /tmp/quickshare-docker-compose
sudo install -m 0755 /tmp/quickshare-docker-compose /usr/local/bin/docker-compose
/usr/local/bin/docker-compose version
sudo /usr/local/bin/docker-compose version
```

`v5.5.0` 是本文校对时官方独立版安装页使用的版本示例，不要求现有服务器升级到这个版本。后文统一使用带连字符的 `sudo docker-compose`，不要求将普通用户加入 Docker 管理组。`docker-compose.yml` 和 `docker-compose.ip.yml` 是配置文件名，不需要改名。

## 3. 上传项目

### 3.1 创建目录

先通过 SSH 登录服务器，用实际部署账号执行：

```bash
sudo mkdir -p /opt/quickshare
sudo chown "$(id -un):$(id -gn)" /opt/quickshare
```

### 3.2 从 Windows 上传

在本地 PowerShell 执行，替换项目路径、SSH 账号和 IP：

```powershell
Set-Location "E:\Github Repo\OBS"
scp -r .\deploy .\server deployuser@203.0.113.10:/opt/quickshare/
```

如果 SSH 使用其他端口，给 `scp` 加 `-P 端口号`。上传至少需要下面这些文件：

```text
/opt/quickshare/
├── deploy/
│   ├── docker-compose.yml
│   ├── docker-compose.ip.yml
│   ├── livekit.yaml
│   └── caddy/Caddyfile
└── server/
    └── token-service/
        ├── Dockerfile
        ├── server.mjs
        └── config.example.json
```

必须保留 `deploy` 与 `server` 的相对位置，Compose 使用 `../server/token-service` 作为构建上下文。无需上传 Windows 的 `livekit-server.exe`、Electron 依赖或客户端打包产物。

服务器上确认文件存在，然后进入部署目录：

```bash
test -f /opt/quickshare/server/token-service/server.mjs
test -f /opt/quickshare/deploy/livekit.yaml

```

## 4. 方案 A：域名与 HTTPS

本节是推荐的公网部署方案。下面 Compose 命令统一使用项目名 `quickshare`；以后维护也使用同一项目名和同一目录。

### 4.1 配置 DNS

为 `share.example.com` 创建 A 记录，指向服务器公网 IPv4。

- 初次部署使用 DNS 直连模式；如果 DNS 服务提供商有 HTTP CDN 代理功能，先关闭代理。媒体 UDP 不通过普通网站 CDN。
- 没有正确配置 IPv6 时，不要保留指向其他主机的 AAAA 记录。
- 从服务器外部确认 DNS 结果：Windows 可运行 `Resolve-DnsName share.example.com`，Linux 可运行 `getent ahostsv4 share.example.com`。

Caddy 按域名自动申请和续期 HTTPS 证书，需要 DNS 正确且 80/443 从公网可达。详见 [Caddy HTTPS 说明](https://caddyserver.com/docs/quick-starts/https)。

### 4.2 放行云安全组与主机防火墙

在云厂商的安全组或外部防火墙中配置：

| 端口 | 协议 | 公网放行 | 用途 |
| --- | --- | --- | --- |
| SSH 实际端口，通常 22 | TCP | 仅管理员来源 IP | 远程管理 |
| 80 | TCP | 是 | HTTP 跳转、证书验证 |
| 443 | TCP | 是 | HTTPS API、WSS 信令 |
| 7881 | TCP | 是 | ICE/TCP 媒体回退 |
| 3478 | UDP | 是 | 内置 TURN/UDP |
| 50000–60000 | UDP | 是 | WebRTC 媒体 |
| 7880 | TCP | 否 | LiveKit 内部 API/信令，由 Caddy 代理 |
| 8080 | TCP | 否 | Token 容器内部端口，没有发布到宿主机 |

UFW 示例适用于专用服务器；已有防火墙规则时，按现有策略追加。启用 UFW 前先放行**实际 SSH 端口**，并保留当前 SSH 会话：

```bash
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 7881/tcp
sudo ufw allow 3478/udp
sudo ufw allow 50000:60000/udp
sudo ufw enable
sudo ufw status verbose
```

LiveKit 使用 host 网络，监听 7880 时需由云安全组和主机规则限制公网入口。Docker 发布的容器端口可能绕过 UFW 的常规规则，因此也要检查云安全组，不能只依赖 UFW。参见 [Docker 防火墙说明](https://docs.docker.com/engine/network/packet-filtering-firewalls/)。

### 4.3 生成两个不同的秘密

在 `/opt/quickshare/deploy` 执行：

```bash
umask 077
printf 'LIVEKIT_API_SECRET=%s\nAUTH_TOKEN=%s\n' \
  "$(openssl rand -hex 32)" "$(openssl rand -hex 32)" > .env
chmod 600 .env
```

这条命令用于**首次创建** `.env`。已有部署不要重复执行，否则会覆盖现有密钥。

- `LIVEKIT_API_SECRET`：服务端签发 LiveKit JWT 的秘密，只供管理员使用。
- `AUTH_TOKEN`：团队 API 访问令牌，填写到所有获准使用的客户端。
- 房间口令：共享者自己设置，只限制观看该房间。
- `ownerToken`：每次建房由 API 返回，只允许该共享者结束对应房间。

这四者用途不同。不要把 LiveKit API Secret 分发给客户端，也不要把 `.env` 上传到公开仓库、工单或截图。

### 4.4 修改 LiveKit 密钥

```bash
nano .env
nano livekit.yaml
```

把 `.env` 中 `LIVEKIT_API_SECRET=` 后面的完整值复制到 `livekit.yaml` 的 `keys`，替换默认 `secret`：

```yaml
keys:
  devkey: "这里填写实际的 LIVEKIT_API_SECRET"
```

`devkey` 在这里是 API Key 名称，可以保留；真正必须更换的是 API Secret。若修改名称，还必须同步修改 Token 容器的 `LIVEKIT_API_KEY`。

**`livekit.yaml` 不会自动读取 Compose 的 `.env`，也不会展开 `${LIVEKIT_API_SECRET}`。必须填入实际密钥。** Compose 环境变量和挂载进去的 YAML 是两条独立的配置链路。

公网 VPS 保留：

```yaml
port: 7880
rtc:
  tcp_port: 7881
  port_range_start: 50000
  port_range_end: 60000
  use_external_ip: true
turn:
  enabled: true
  udp_port: 3478
```

### 4.5 修改 Token 服务环境变量

```bash
nano docker-compose.yml
```

将 `token.environment` 中对应项目改为：

```yaml
    environment:
      LISTEN: 0.0.0.0:8080
      LIVEKIT_HTTP_URL: http://host.docker.internal:7880
      LIVEKIT_WS_URL: wss://share.example.com
      LIVEKIT_API_KEY: devkey
      LIVEKIT_API_SECRET: ${LIVEKIT_API_SECRET:?必须在.env中填写LIVEKIT_API_SECRET}
      AUTH_TOKEN: ${AUTH_TOKEN:?必须在.env中填写AUTH_TOKEN}
      REQUIRE_AUTH: "1"
```

把信令地址中的域名换成真实域名。保留 Token 容器和 Caddy 容器各自的 `extra_hosts`：

```yaml
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

当前域名模板允许不配置 API 令牌；本文部署步骤通过必填插值和 `REQUIRE_AUTH: "1"` 强制开启鉴权。TLS 保护传输，API 令牌控制谁能使用服务，两者都需要配置。

### 4.6 修改 Caddy 域名

```bash
nano caddy/Caddyfile
```

文件内容如下，首行换成真实域名：

```caddyfile
share.example.com {
    handle /api/* {
        reverse_proxy token:8080
    }
    handle {
        reverse_proxy host.docker.internal:7880
    }
}
```

保留 `handle /api/*`，不要换成会剥离 `/api` 前缀的 `handle_path`，因为 Token 服务路由本身包含 `/api`。Caddy 的反向代理支持 WebSocket，无需另加手工 Upgrade 头。参见 [Caddy reverse_proxy 文档](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)。

### 4.7 校验并启动

先限制含密钥文件权限：

```bash
chmod 600 .env livekit.yaml
sudo docker-compose -p quickshare -f docker-compose.yml config --quiet
sudo docker-compose -p quickshare -f docker-compose.yml pull livekit caddy
sudo docker-compose -p quickshare -f docker-compose.yml build token
sudo docker-compose -p quickshare -f docker-compose.yml up -d
sudo docker-compose -p quickshare -f docker-compose.yml ps
sudo docker-compose -p quickshare -f docker-compose.yml logs --tail=100 token caddy livekit
```

预期三个服务都处于运行状态，Token 日志出现 `listening on 0.0.0.0:8080`，Caddy 没有持续的证书申请错误，LiveKit 没有配置或端口绑定错误。模板未定义容器 healthcheck，`running` 只表示进程存在，仍需完成下面的接口和媒体验收。

不带 `--quiet` 的 `docker-compose config` 会展开秘密，不要把输出贴到公开位置。

### 4.8 如 UFW 拦截容器访问宿主机

HTTPS 方案中，Token 和 Caddy 通过 Docker bridge 访问宿主机 7880。若日志显示该连接超时，检查 Compose 网络：

```bash
sudo docker network inspect quickshare_default \
  --format '{{range .IPAM.Config}}{{.Subnet}}{{end}}'
```

例如输出 `172.18.0.0/16`，则允许**实际输出的可信 Docker 子网**访问 7880：

```bash
sudo ufw allow from 172.18.0.0/16 to any port 7880 proto tcp
```

该地址仅为示例，不能盲目照抄。它用于内部容器通信，不需要在云安全组向公网开放 7880。

### 4.9 外部验证

从服务器之外的一台机器执行：

```bash
curl -i https://share.example.com/api/health
curl -i https://share.example.com/api/rooms
```

预期健康接口返回 `200` 和 `{"ok":true}`；未带令牌的房间列表返回 `401`。不要用 `curl -k` 跳过证书校验来代替验收。

在服务器 Bash 中安全地载入 `.env` 后检查带鉴权的列表：

```bash
cd /opt/quickshare/deploy
set -a
source .env
set +a
curl -i https://share.example.com/api/rooms \
  -H "Authorization: Bearer $AUTH_TOKEN"
```

没有共享时预期返回 `200` 和 `{"rooms":[]}`。`/api/health` 只证明 Token HTTP 服务存活；带鉴权的列表查询成功，才同时验证了 Token 到 LiveKit 的 RoomService 连接。

## 5. 方案 B：IP 直连

适合内网、VPN 网络或短期测试。媒体使用 WebRTC 加密，但 `http://` API 和 `ws://` 信令为明文，访问令牌、房间口令和 JWT 会经过这些连接。公网长期运行应使用方案 A。

本节从已完成第 2、3 节的环境开始，Compose 项目名使用 `quickshare-ip`。

### 5.1 防火墙

放行以下入站端口：

| 端口 | 协议 | 用途 |
| --- | --- | --- |
| SSH 实际端口 | TCP | 服务器管理，限制管理员来源 |
| 8080 | TCP | Token API，可限制为获准使用的客户端来源 |
| 7880 | TCP | LiveKit 信令 |
| 7881 | TCP | 媒体 TCP 回退 |
| 3478 | UDP | TURN/UDP |
| 50000–60000 | UDP | WebRTC 媒体 |

对应 UFW 命令如下；还需在云安全组中放行：

```bash
sudo ufw allow 22/tcp
sudo ufw allow 8080/tcp
sudo ufw allow 7880/tcp
sudo ufw allow 7881/tcp
sudo ufw allow 3478/udp
sudo ufw allow 50000:60000/udp
sudo ufw enable
sudo ufw status verbose
```

### 5.2 生成配置并填入密钥

首次部署时，在 `/opt/quickshare/deploy` 执行，把 IP 换成真实服务器地址：

```bash
cd /opt/quickshare/deploy
umask 077
printf 'SERVER_IP=203.0.113.10\nLIVEKIT_API_SECRET=%s\nAUTH_TOKEN=%s\n' \
  "$(openssl rand -hex 32)" "$(openssl rand -hex 32)" > .env
chmod 600 .env
nano .env
nano livekit.yaml
```

把 `.env` 的 `LIVEKIT_API_SECRET` 实际值填到 `livekit.yaml` 的 `keys.devkey`，方法与方案 A 相同。

- 公网 VPS：保留 `rtc.use_external_ip: true`。
- 纯内网服务器：改为 `rtc.use_external_ip: false`，`SERVER_IP` 填所有客户端可访问的服务器内网地址。
- 多网卡、VPN 或 NAT 环境：确保媒体候选地址能被客户端访问。只将 7880/8080 做端口转发并不足以建立媒体连接。
- `SERVER_IP` 不加 `http://`，不包含端口；不要填客户端自己的 IP 或服务器无法被外部访问的 `127.0.0.1`。

### 5.3 启动

当前 `docker-compose.ip.yml` 已设置 `REQUIRE_AUTH: "1"`，访问令牌为空时 Token 服务会拒绝启动。启动前确认 `.env` 三个变量均已填写：

```bash
sudo docker-compose -p quickshare-ip -f docker-compose.ip.yml logs --tail=100 token livekit
```

本配置使用 Linux host 网络，因此映射规则在现有外部入口配置，不在 Compose 中添加 `ports`。媒体端口仍按第 5.1 节和实际网络配置保持可达，完成两个客户端的共享、观看验证。

## 7. API 与业务验收

### 7.1 接口合同

除 `/api/health` 和 CORS 预检外，开启鉴权后业务请求都要带 `Authorization: Bearer <AUTH_TOKEN>`。

| 请求 | 主要请求体 | 成功结果 |
| --- | --- | --- |
| `GET /api/health` | 无 | `200`，`ok: true` |
| `GET /api/rooms` | 无 | `200`，仅列出有发布者的房间 |
| `POST /api/rooms` | `roomId`、`presenter`、可选 `password` | `201`，返回 `token`、`url`、`ownerToken` |
| `POST /api/rooms/:id/join` | `name`、可选 `password` | `200`，返回仅订阅 Token |
| `DELETE /api/rooms/:id` | `ownerToken` | `200`；房间已不存在则 `404` |

房间号长度 1～32，不能包含控制字符。同号已存在返回 `409`；删除时缺少或伪造管理凭证返回 `403`。房间号放入 URL 时需 URL 编码。

### 7.2 用脚本验证建房、口令和房主管理

下面在服务器 Bash 执行，先在当前终端按前文加载 `.env`。HTTPS 方案设置第一行；IP 方案改用注释中的地址。脚本创建临时房间，不发布视频，所以不会出现在活跃列表中。建房仍会占用房间号，最后会删除。

```bash
export TEST_BASE_URL="https://share.example.com"
# IP 方案改为：export TEST_BASE_URL="http://203.0.113.10:8080"

python3 - <<'PY'
import json, os, urllib.request, urllib.error, uuid

base = os.environ['TEST_BASE_URL'].rstrip('/')
auth = os.environ['AUTH_TOKEN']
room = 'check-' + uuid.uuid4().hex[:12]
owner = None

def request(method, route, body=None):
    data = None if body is None else json.dumps(body).encode()
    req = urllib.request.Request(base + route, data=data, method=method,
        headers={'Content-Type': 'application/json',
                 'Authorization': 'Bearer ' + auth})
    try:
        with urllib.request.urlopen(req, timeout=15) as response:
            return response.status, json.load(response)
    except urllib.error.HTTPError as response:
        return response.code, json.load(response)

try:
    status, created = request('POST', '/api/rooms',
        {'roomId': room, 'presenter': 'deployment-check', 'password': 'check-password'})
    assert status == 201, (status, created.get('error'))
    owner = created['ownerToken']
    status, _ = request('POST', '/api/rooms', {'roomId': room})
    assert status == 409, status
    status, _ = request('POST', '/api/rooms/' + room + '/join', {'password': 'wrong'})
    assert status == 401, status
    status, joined = request('POST', '/api/rooms/' + room + '/join', {'password': 'check-password'})
    assert status == 200, (status, joined.get('error'))
    assert 'ownerToken' not in joined
    status, _ = request('DELETE', '/api/rooms/' + room, {'password': 'check-password'})
    assert status == 403, status
    status, _ = request('DELETE', '/api/rooms/' + room, {'ownerToken': owner})
    assert status == 200, status
    owner = None
    status, _ = request('POST', '/api/rooms/' + room + '/join', {})
    assert status == 404, status
    print('PASS: 建房、重复房间、口令校验、删除权限、删房后不可进入')
finally:
    if owner:
        status, _ = request('DELETE', '/api/rooms/' + room, {'ownerToken': owner})
        if status not in (200, 404):
            print('清理失败，请检查临时房间：', room, status)
PY
```

脚本不会输出 JWT、管理凭证或访问令牌。接口检查通过只能证明控制面正常，还需验证下面的真实画面。


### 8.3 备份配置、源码和证书卷

示例部署备份包含秘密，设置严格权限。为得到一致的 Caddy 卷备份，在维护窗口执行：


IP 方案没有 Caddy 卷，只需要配置和源码备份。将备份复制到受控的异机位置；不能把备份目录当成可恢复的活动房间数据库。

### 8.4 升级

先备份并记录当前镜像：

```bash

sudo docker image inspect livekit/livekit-server:latest --format '{{json .RepoDigests}}'
```

模板使用 `livekit/livekit-server:latest` 和 `caddy:2-alpine`，标签会变化。正式运行应将 Compose 的 `image` 固定为经本环境验收的版本标签或 digest，并保存对应配置与镜像版本记录。

只升级 Token 代码：上传新的 `server/token-service` 后执行：

```bash
sudo docker-compose -p quickshare -f docker-compose.yml build token
sudo docker-compose -p quickshare -f docker-compose.yml up -d --no-deps token
```

升级 LiveKit/Caddy：修改已确认的镜像版本后执行：

```bash
sudo docker-compose -p quickshare -f docker-compose.yml pull livekit caddy
sudo docker-compose -p quickshare -f docker-compose.yml up -d
```

LiveKit 重建会中断媒体。升级完成后重新执行健康、鉴权、接口和跨网络媒体验收。若涉及 API 协议变化，同时升级客户端。

### 8.5 回滚

1. 安排维护窗口，停止当前项目。
2. 从备份恢复旧版 `deploy`、`server` 和原有 `.env`；不要生成新的密钥。
3. 将 LiveKit/Caddy 的 `image` 恢复为记录的版本或 digest。
4. 重建旧版 Token 镜像，再运行 `up -d`。
5. 重新验收，并通知共享者重新开始共享。

恢复配置时保留原有 Caddy 数据卷。不要用 `docker-compose down -v` 作为普通更新命令，它会删除此项目的命名卷。

### 8.6 密钥轮换

- 轮换 `AUTH_TOKEN`：更新 `.env` 并重建 Token 服务，所有客户端同步更新访问令牌。它不会主动撤销已经发出的 LiveKit JWT，也不会立即断开现有媒体会话。
- 轮换 LiveKit API Secret：同时改 `livekit.yaml` 和 `.env`，在维护窗口重新创建相关容器。原 JWT 和旧房间口令摘要不再按新密钥有效，共享者需要重建房间。
- 如需立即停止已有访问：明确结束相关房间；仅改团队访问令牌不足以实现这一点。

## 9. 配置项说明

### 9.1 Token 服务环境变量

| 变量 | 默认/示例 | 说明 |
| --- | --- | --- |
| `LISTEN` | `0.0.0.0:8080` | Token HTTP 监听地址，当前解析逻辑使用 IPv4 地址格式 |
| `LIVEKIT_HTTP_URL` | 域名方案 `http://host.docker.internal:7880` | 服务端访问 RoomService 的内部地址 |
| `LIVEKIT_WS_URL` | `wss://share.example.com` | 下发给客户端的信令地址，必须从客户端网络可达 |
| `LIVEKIT_API_KEY` | `devkey` | 必须与 `livekit.yaml` 的 keys 名称一致 |
| `LIVEKIT_API_SECRET` | 随机 64 位十六进制字符串 | 必须与 keys 中的秘密完全一致 |
| `AUTH_TOKEN` | 随机令牌 | 客户端 API 访问令牌 |
| `REQUIRE_AUTH` | `1` | 强制检查访问令牌非空，缺失时拒绝启动 |
| `CONFIG_PATH` | `/app/config.json` 的默认路径 | 可指定挂载的自定义 JSON 配置文件 |

同名环境变量覆盖 JSON 中的对应配置；空环境变量也会覆盖 JSON，所以不要把空字符串当成“未配置”。

### 9.2 房间参数

房间参数目前从 JSON 的 `rooms` 读取，没有对应的独立环境变量：

```json
{
  "rooms": {
    "tokenTtlMinutes": 240,
    "requirePassword": false,
    "maxRoomIdLength": 32,
    "emptyTimeoutSeconds": 60
  }
}
```

- `tokenTtlMinutes`：签发的连接 Token 有效期；不是共享会话的强制结束定时器。
- `requirePassword`：开启后，创建房间必须有口令。
- `maxRoomIdLength`：服务端长度上限；客户端 UI 当前最多 32 字符。
- `emptyTimeoutSeconds`：LiveKit 空房间超时，同时用于后台清理无发布者房间的宽限期。不要设为 0，除非专门做清理测试。

镜像默认使用仓库中的 `server/token-service/config.example.json`。实际 JSON 配置不提交到 Git；如需自定义房间参数，先在部署服务器创建本地配置，再在 Token 服务下挂载：

```bash
# 只在 config.json 尚不存在时执行，不覆盖已有配置。
test -f ../server/token-service/config.json || \
  cp ../server/token-service/config.example.json ../server/token-service/config.json
nano ../server/token-service/config.json
```

```yaml
    volumes:
      - ../server/token-service/config.json:/app/config.json:ro
```

增加挂载需 `up -d` 应用，后续修改挂载的 JSON 后可 `restart token` 使其重新读取。容器运行用户为 `node`，挂载文件需要对该用户可读；此 JSON 可只保存房间参数，实际秘密仍通过 `.env` 的环境变量传入。服务启动时只读一次配置；JSON 必须有效，可用 `python3 -m json.tool ../server/token-service/config.json > /dev/null` 检查。

### 9.3 TURN/TLS 的边界

当前模板只启用 TURN/UDP 3478。公司网络若同时禁止 UDP 和 7881/TCP，可能无法观看，需要额外设计 TURN/TLS。

**不能只取消 `tls_port` 注释就认为配置完成。** 内置 TURN/TLS 需要合适的 TURN 域名、证书与私钥，并规划 TCP 443 或四层负载均衡。当前 Caddy 已占用宿主机 TCP 443；HTTP 反向代理不能直接转发任意 TURN/TLS 流量，需要独立 IP/服务或支持该场景的四层入口。LiveKit 官方要求自行提供其 TLS 终止使用的证书文件，详见 [LiveKit TURN 部署说明](https://docs.livekit.io/transport/self-hosting/deployment/)。

不要假设 LiveKit 会自动向 Let's Encrypt 申请 TURN 证书；当前模板也未配置这一流程。

## 10. 故障排查

| --- | --- | --- |
| `/api/health` 超时 | DNS、云安全组、UFW、进程未启动 | 外部 curl、`compose ps`、`ss -lntup` |
| HTTPS 证书错误 | DNS 错误、错误 AAAA、80/443 被占用或阻断 | Caddy 日志、DNS 解析、端口监听 |
| 列表返回 401 | 客户端令牌为空或与服务端不同 | 检查设置和 `.env` 的 AUTH_TOKEN |
| 健康 200、列表 502/500 | Token 到 LiveKit 不通或密钥不同 | Token 日志、内部 RoomService 探测 |
| `host.docker.internal` 无法解析 | Linux 容器缺少 extra_hosts | 检查 token 与 caddy 都有 host-gateway 映射 |
| Token 容器不断重启 | REQUIRE_AUTH=1 但令牌空，或端口占用 | `logs token`、`.env`、`ss` |
| 显示服务器在线但共享无画面 | UDP/TCP 媒体端口未放行、候选 IP 不可达 | 云安全组、跨网络测试、LiveKit 日志 |
| 建房返回 409 | 房间已存在，或旧房间等待清理 | 停止原共享、换号、等待宽限期 |
| 删除返回 403 | 旧客户端、丢失 ownerToken、观众尝试删除 | 升级客户端；房间口令不授予删除权限 |
| 升级后旧口令房返回 503 | 升级前房间缺少新权限摘要 | 结束旧共享并重新建房 |
| 仅公司网络无法观看 | 严格防火墙阻断媒体通道 | 换热点对照，评估 TURN/TLS |
| 修改 env 后没有效果 | 只 restart，没有重新创建容器 | 使用 `up -d`，代码变化还要 build |
| Docker 提示没有 compose 子命令 | 当前安装的是独立命令 | 使用本文的 `docker-compose`，不使用空格写法 |
| sudo 找不到 docker-compose | sudo 的 PATH 不包含命令目录 | `command -v docker-compose`，使用实际绝对路径 |
| 提示 services 为不支持的配置项 | Compose 版本过旧，不支持当前格式 | 检查版本，按第 2.2 节升级独立命令 |

### 10.1 HTTPS 内部链路探测

在部署目录执行：

```bash
sudo docker-compose -p quickshare -f docker-compose.yml exec -T token \
  node -e "fetch('http://127.0.0.1:8080/api/health').then(async r=>console.log(r.status,await r.text())).catch(e=>{console.error(e.message);process.exitCode=1})"

sudo docker-compose -p quickshare -f docker-compose.yml exec -T token \
  node -e "fetch(process.env.LIVEKIT_HTTP_URL).then(r=>console.log('LiveKit HTTP status:',r.status)).catch(e=>{console.error(e.message);process.exitCode=1})"
```

第二条只检查网络可达性。LiveKit 根路径返回 404 也可说明 HTTP 连接已建立，不代表 RoomService 鉴权通过；业务列表查询成功才验证完整链路。

### 10.2 如何判断是不是端口问题

```bash
sudo ss -lntup
sudo docker-compose -p quickshare -f docker-compose.yml logs --tail=200 livekit
```

Windows 可检查 TCP：

```powershell
Test-NetConnection share.example.com -Port 443
Test-NetConnection share.example.com -Port 7881
```

TCP 检查不能验证 UDP 或完整 WebRTC 协商。也不能因为服务器本机 curl 成功，就认为公网已经可用；必须从另一条网络进行真实客户端测试。
